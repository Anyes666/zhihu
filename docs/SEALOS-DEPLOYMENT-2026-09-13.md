## 已遇到并处理的问题

1. 本机 Git 推送连接失败：改用 GitHub 官方 Git 数据 API，核对提交与完整文件树一致，未强推覆盖远端。
2. 第一次 CI 误把关闭模型配置施加给所有测试：本地复现其对 mock 的干扰后移除全局配置、增加回归测试，最终 CI 通过。
3. Sealos 直接下载 GitHub 归档超过 120 秒超时：最终改为通过已授权的 Kubernetes API 交付分块源码，新的初始化已成功。
4. 文档追加时发现 PowerShell 到 Python 的编码问题：已用 UTF-8 重写新增段落并检查，不影响游戏运行源码。
5. 最后的 Cookie 检查最初错误地要求经典模式签发预算 Cookie：核对源码后确认经典模式按设计不签发，改为验证该行为；没有为测试打开真实 API。

## 运维、恢复与边界

- 本地部署证据位于 `artifacts/sealos-deploy-2026-09-13/`，不随仓库上传：`release.json`、`source.tar.gz`、`public-security-check.json`、`public-audit/browser-exploratory/browser-report.json`、CI 日志及最终资源快照。
- `deployment-before.json` 与 `service-before.json` 是原始 Nginx 配置的备份，不是可玩游戏版本。最终可玩配置另存为 `deployment-current.json` 与 `service-current.json`；源码分块可依据归档和 release 清单重建。恢复时应使用当前授权的本地 Kubeconfig，先做服务端 dry-run，不能直接覆盖已变化的云端资源。
- 本地已有的四处未提交 API 无限用量相关修改保留原样，没有混入此次部署发布。线上仍是原来的安全预算逻辑，且总开关关闭。
- 没有启用或验证真实付费 API。开启前需批准预算、配置服务端 Secret、持久化预算账本；不要把本地 `.env` 整份复制到仓库、网页或聊天。
- 会话保存在单进程内存中，重启或更新会丢失正在进行的游戏局；本次没有额外执行线上重启测试或大规模压力测试。
- 平台资源仍可能持续计费；需在 Sealos 关注余额。未核验计费余额或剩余可运行时长，不承诺永久免费或任意并发。
- 本次完成的是一次可验证的部署，不是自动持续部署：后续 GitHub 代码更新不会自动替换当前固定源码包，需重新验证与发布。
