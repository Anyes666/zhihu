# 技术方案 · 回声邮局

> 2026-09-13 已升级知乎参考台。最新能力与验收证据见 [ZHIHU-UPGRADE.md](ZHIHU-UPGRADE.md)。

## 一、总体架构

```
浏览器（原生 ES Module，无框架无构建）
   │  fetch + SSE
   ▼
server.mjs（Node 原生 http，无框架）
   ├── 静态资源
   ├── 游戏 API（会话内存态，6 小时 TTL）
   │      │
   │      ├── lib/engine.mjs   纯逻辑：状态机 / 评分 / 真相 / 结局
   │      ├── lib/zhihu.mjs    知乎适配：频控 + 两级缓存 + 降级
   │      └── lib/llm.mjs      AI 分层：Prompt / 流式 / 降级
   ▼
知乎开放平台（热榜 / 站内搜索 / 直答）
   └── 不可用时 → data/demo/*.json
```

**零依赖。** `package.json` 没有 `dependencies`，全部用 Node 20+ 内置能力（`fetch`、`http`、`node:test`）。评审拉下仓库 `npm start` 就能跑，不需要 `npm install`。

## 二、AI 分层：事实与表达分离

这是全项目最关键的设计决策。

### 问题

如果让模型直接决定剧情，会有三个致命后果：玩法不可测（模型随机性）、会幻觉出不存在的事实、模型不可用时游戏完全瘫痪。

### 方案

```
玩家提问
   │
   ▼
engine.classifyAttitude()  ──→ 态度（5 类，正则判定，零延迟）
   │
   ▼
engine.ask()               ──→ 信任度变化 + 真相是否解锁 + 事实骨架台词
   │                            （全部确定性，可单测）
   ▼
llm.characterMessages()    ──→ 注入：人设 + 事实骨架 + 态度 + 真相授权 + 社区语料
   │
   ▼
llm.streamChat()           ──→ 流式生成最终台词
   │
   ├─ 成功且通过校验 → 用模型文本展示
   └─ 失败/超时/跑偏 → 用事实骨架本身展示（逐字流式模拟）
```

**模型只负责"怎么说"，不决定"说什么事实"。** Prompt 里的硬约束：

> 你的回答必须以下面这段「事实骨架」为唯一的事实来源，可以改写语气、补充细节感受，但不能新增或改变任何事实、日期、数字、人物关系。

**输出校验不是语义真实性保证，仅检查长度和格式。**

**输出校验：** 长度 ≥ 12 字（去空格）且不含 `[`、`]`、`**`、行首 `#`。不合格则发 `reset` 事件让前端清空半截内容，再流式回放规则台词。

### 三重降级

| 失败情形 | 处理 | 玩家感知 |
| --- | --- | --- |
| 未配置任何 LLM 凭证 | 直接走规则台词 | 台词略朴素，玩法完整 |
| 请求超时（9 秒）/ HTTP 错误 / 流中错误 | 发 `notice` 提示，回退规则台词 | 一条"已切换为规则台词"的提示 |
| 模型输出跑偏（markdown / 过短） | 发 `reset` 清空，回退规则台词 | 短暂闪烁后显示正常台词 |

三种情形都有测试覆盖（`tests/llm.test.mjs`、`tests/server.test.mjs`）。

### 供应商优先级

```
显式 LLM_PROVIDER 优先（deepseek / openai / zhida / none）
   → 未显式指定时：兼容模型配置完整则优先，否则知乎直答
      → 不可用时回退规则引擎，不跨供应商自动重试
```

知乎直答的 Chat Completions 接口与 OpenAI 兼容，两条路径共用同一套流式解析（含 `: keep-alive` 心跳注释的跳过处理）。

## 三、知乎开放平台适配

### 接口调用

| 能力 | 端点 | 缓存 | 本地频控 |
| --- | --- | --- | --- |
| 热榜 | `GET /api/v1/content/hot_list` | 30 分钟 | 4 次/分 |
| 站内搜索 | `GET /api/v1/content/zhihu_search` | 6 小时 | 30 次/分 |
| 知识列表 | `GET https://api.zhihu.com/km-indep-home/hackathon/v2/knowledge/list` | 6 小时 | 10 次/分 |
| 直答 | `POST /v1/chat/completions` | 不缓存 | 10 次/分 |

热榜、搜索与直答鉴权按平台要求（活动知识列表不带鉴权）：`Authorization: Bearer <secret>` + `X-Request-Timestamp`（秒级）。

### 为什么要本地频控

邀测阶段热榜和直答的日额度都只有 100 次，而且同账号下所有 Access Secret 共享同一额度池。路演现场如果有人反复刷新页面，几分钟就能把额度耗光。

单进程滑动分钟窗口与自然日计数按能力独立保护（重启/多实例不共享），超限时不发请求，直接走缓存或演示包——**保护额度比拿到最新数据重要。**

### 两级缓存

内存 Map（进程内，最快）→ 磁盘 `data/cache/*.json`（跨重启保留）。命中任一级且未过期即返回，并在响应里标注 `source: "cache"`。

请求失败时的兜底顺序：内存里的过期数据（`source: "cache"` + `stale: true` + `fallbackReason`）→ 演示包（`source: "demo"`）。

### 题材联动的实现

每封信声明一组热榜匹配关键词（如 `"父母 子女 离家 异地"`）。`matchHot()` 对热榜条目做关键词计数，取命中最多的一条。命中 0 条时用该信预设的兜底话题，标注 `source: "fallback"`。

这样做的原因：热榜每天都变，不能假设一定有匹配的话题。**宁可标注"关联话题"，也不硬凑一个不相关的热榜条目。**

### 来源透明

每一处引用知乎数据的 UI 都带来源标记：

- 绿点「实时」= 本次真实调用了接口
- 琥珀点「缓存」= 命中本地缓存
- 琥珀点「演示快照 / 演示素材包」= 走了降级

页面右上角显示模型配置；各资料卡展示本次实际数据来源及获取时间。配置状态不是联网成功证明。**不假装实时是产品诚信的一部分**，评审一眼能看出哪些是真接口、哪些是兜底。

## 四、流式设计

三个接口走 SSE：角色对话、回信点评、结局旁白。

事件协议：

| 事件 | 载荷 | 时机 |
| --- | --- | --- |
| `meta` / `scores` / `ending` | 引擎算好的结构化结果 | 第一个事件，立刻发出 |
| `delta` | 文本分片 | 生成过程中 |
| `notice` | 降级提示 | LLM 失败时 |
| `reset` | 空 | 需要清空已流出内容时 |
| `done` | 最终文本 + 会话快照 | 最后一个事件 |
| `error` | 错误信息 | 流已开始后出错 |

**结构化结果先于文本流发出**，前端可以立刻渲染评分条、雷达图、信任度变化，文字再慢慢流进来。这让"3 秒内响应"这件事在体感上成立：即使模型要 5 秒才说完第一句，玩家在 200 毫秒内就看到了态度判定和信任度变化。

规则台词也做逐字流式（每 6 字一片、18 毫秒间隔），让降级路径的手感与模型路径一致。

## 五、会话与状态

会话存在内存 `Map`，6 小时 TTL，每 10 分钟清理。不落库，因为单局只有 3–5 分钟，且没有跨设备需求。

前端把 `sessionId` 存进 `sessionStorage`，刷新页面后调 `/state` 拉回完整状态并恢复到对应阶段。服务端返回的 `bundle()` 包含会话状态、信件视图、刘看山台词、角色身份映射——**一次请求就能重建整个界面**，不需要前端缓存业务数据。

## 六、前端

原生 ES Module，单文件 `public/app.js`，无框架无构建。

- 状态集中在一个 `S` 对象，每个阶段一个 `render*` 函数，整段替换 `#app`
- 雷达图用手写 SVG（多边形 + 坐标计算），不引图表库
- 档案卡用 Canvas 绘制（牛皮纸底图 + 文字排版 + 进度条），可导出 PNG
- 拖拽分拣同时支持 HTML5 drag 和"先点句子再点分类框"，后者是移动端主路径

### 两个修掉的真实缺陷

**1. 召唤与提问的竞态。** 点击角色卡后，`summon` 的网络请求返回前输入框仍然可用。玩家（或自动化脚本）此时提问，会把问题发给**上一个**角色，并白白消耗一枚邮票。修法：`S.busy` 互斥锁 + `lockInput()` 统一控制输入态，`ask()` 内把角色 ID 固定为发起时的值。

**2. 按钮渲染早于事件绑定。** 评分结果一到就渲染了"封印寄出"按钮，但 `onclick` 要等文本流结束才绑定。中间这几秒玩家点了没反应。修法：把绑定移到 `scores` 事件处理器里，与按钮渲染同步完成。

**3. 动画依赖 requestAnimationFrame。** 五维条与社区票数的入场动画原本走 rAF。浏览器在后台标签页会暂停 rAF，玩家切走再切回来，条形会永久停在 0、票数停在 0。修法：条形改用 `setTimeout` 触发 CSS transition，票数改用 `setInterval` 计数并先落终值。

三个问题都是在浏览器自动化验证时暴露的，靠读代码不容易发现。

数据完整性测试是刻意写的：它会检查每封信的六类分拣是否齐全、每层真相是否至少有一个知情角色备有对应台词、4×3 结局矩阵是否有空缺。**新增信件时，漏写任何一块都会立刻失败。**

## 八、美术资源

脚本幂等：`assets-src/` 里已有的图跳过生成，只重做压缩。

## 九、部署

纯静态 + 单进程 Node，任何支持 Node 20 的平台都能跑。

```bash
PORT=8080 ZHIHU_ACCESS_SECRET=<secret> npm start
```

服务默认监听 `0.0.0.0`，容器化无需改动。见 [DEPLOY.md](DEPLOY.md)。

环境变量（全部可选）：

| 变量 | 作用 | 不配的后果 |
| --- | --- | --- |
| `ZHIHU_ACCESS_SECRET` | 知乎热榜/搜索/直答 | 走演示数据包 + 规则台词 |
| `LLM_BASE_URL` + `LLM_API_KEY` | 备用 OpenAI 兼容端点 | 无备用 LLM |
| `LLM_MODEL` | 备用端点模型名 | 默认 `gpt-4o-mini` |
| `PORT` / `HOST` | 监听地址 | `3000` / `0.0.0.0` |
